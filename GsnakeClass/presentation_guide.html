COSC 481 — Presentation Guide & Design Reference

Presentation Structure

  1. Live demo — Run the game. Collect something, die, show the score screen. Let them see what they're about to hear explained.
  2. File tour (1 min) — Show the 5-file structure and explain the division: main.py is logic, ui.py is rendering, camera.py / collectible.py / settings.py are focused modules. State the rule: rendering never writes back to game state.
  3. Walk one frame — Trace input → physics tick → collision check → render. This ties everything together naturally.
  4. Go deep on 2–3 design decisions — Don't try to cover everything. Pick the ones you're most confident defending and go deep.
  5. End with what you'd do differently — Instructors love honest reflection. It shows you understand the tradeoffs, not just the code.

Key Design Decisions to Highlight

1. Logic vs. Rendering Separation

Game logic lives in main.py; all drawing lives in ui.py. The Renderer class in ui.py receives game objects as parameters and reads their state — it never writes back. Data flows one direction: logic → rendering.

This means you could swap out pyray for a different graphics library by only touching ui.py and camera.py — the physics, collision, and save logic in main.py would be untouched.

Why did you separate rendering from logic?

Maintainability. If a drawing function breaks, the bug is in ui.py. If physics breaks, the bug is in main.py. The two concerns can't interfere with each other.

2. Fixed-Timestep Physics Loop

Physics runs at exactly 60 Hz regardless of frame rate using an accumulator pattern in Game._update(). Real frame time accumulates into a buffer; physics ticks batch-process when the accumulator reaches FIXED_DT = 1/60 s. The accumulator is clamped at MAX_ACCUMULATOR (0.2 s) to prevent a "death spiral" on slow machines.

What happens if the game runs at 30 FPS or 120 FPS?

Physics stays deterministic. The accumulator catches up with multiple ticks on slow frames, or waits on fast frames. Game behavior is identical regardless of display refresh rate.

3. Sweep-Based Collision — No Tunneling

_segment_hits_rect() in main.py tests the movement segment (previous position → current position) against obstacles using parametric segment-rectangle intersection. This prevents the snake from clipping through thin walls at high speed, which a simple point-in-rect test would miss.

A broad-phase AABB cull (only test obstacles within LOOKAHEAD = 200 px ahead of the player) keeps the per-frame cost low even with many obstacles.

How does collision detection work at high speeds?

We test the full movement segment each tick, not just the current position. This is called a sweep test and it guarantees the snake can't skip through an obstacle no matter how fast it moves.

Do you check for self-collision?

No — and deliberately so. The snake always moves rightward, so x strictly increases each tick. The head can never geometrically reach a previous trail point. Skipping that check is correct, not an oversight.

4. Data-Driven Level Design

Levels are entirely defined in JSON files — obstacles, collectibles, speed curve, camera config, and parallax seed. No code changes are needed to add a new level; you only register its path in the GAME_LEVELS list in main.py. 

{
  "name": "Cave Run",
  "length": 5000,
  "speed_curve": [{"x": 0, "mult": 1.0}, {"x": 5000, "mult": 2.2}],
  "camera": {"lookahead": 160, "lerp": 0.08},
  "parallax_seed": 42,
  "obstacles": [...],
  "collectibles": [...]
}

How would you add a new level?

Create a JSON file following the schema and add one line to GAME_LEVELS in main.py. No other code changes needed.

5. Piecewise-Linear Speed Curve

Each level JSON defines a speed curve as a list of waypoints (x world position → mult speed multiplier). Level.speed_at(x) linearly interpolates between them. This gives each level a custom difficulty ramp — early sections easy, late sections punishing — without hardcoding anything.

How does the game get harder over time?

The speed curve increases the player's horizontal velocity as they progress. The same obstacles become harder to dodge because you have less reaction time.

6. Particle Object Pool

ParticleSystem in ui.py pre-allocates 200 particles at startup and recycles them — zero memory allocation during gameplay. When a collectible is picked up or the player dies, the system finds dead particles in the pool and reuses them. If the pool is exhausted, it silently emits fewer particles rather than crashing.

Why not just create particle objects on the fly?

Frequent allocation triggers garbage collection, which causes frame hitches in real-time games. Pooling keeps memory pressure flat and frame times consistent.

7. Two-Pass Trail Rendering

The trail is drawn in two passes inside TrailRenderer in ui.py:

  • Glow pass — wider, semi-transparent, covers only the head region. Width scales with the current speed multiplier.
  • Core pass — full trail drawn as a tapered quad mesh. Colors shift from cyan (level start) → magenta (level end) based on progress.

This creates a glowing aura effect without expensive post-processing.

8. Deterministic Procedural Parallax

ParallaxBackground generates its background rectangles using a seeded random number generator (random.Random(seed)). The same seed always produces the same background. Each level specifies its own parallax_seed in JSON, giving each level a visually unique background with no asset files needed.

How do you get a different background per level without image files?

Each level has a different parallax_seed integer in its JSON. The background generator uses that seed to produce a deterministic but unique arrangement of rectangles. Same seed always gives the same background.

How One Frame Works

Game.run() — each iteration:

  1. dt = get_frame_time()          (real wall-clock delta, e.g. 0.016 s)

  2. _update(dt)
       match self.state:
         MENU         → handle menu input, transition to PLAYING on selection
         PLAYING      → accumulate dt; run fixed physics ticks (_tick):
                          player.heading_up = steering_up
                          Player.update(FIXED_DT)
                          Trail.update(player.pos)
                          Camera.update(player.pos, FIXED_DT)
                          ParticleSystem.update(FIXED_DT)
                          collectible pickup check    ← distance-based radius test
                          boundary + _segment_hits_rect() ← sweep test each obstacle
         PAUSED / GAME_OVER / LEVEL_COMPLETE → handle overlay input

  3. _render()
       progress = player.pos.x / level.level_end_x

       Renderer.draw(progress, player.speed_mult)
         ParallaxBackground.draw()    ← screen space (before camera)
         camera.begin()
           draw obstacles             ← red rectangles
           draw collectibles          ← animated bob, glow ring, type-specific shape
           TrailRenderer.draw()       ← two-pass quad mesh
           draw player                ← two concentric circles
           ParticleSystem.draw()
         camera.end()
       ScreenEffects.draw()           ← screen space (vignette, fade-in)
       HUD.draw()                     ← screen space (score panel, progress bar)
       [menu overlay if not PLAYING]

What You Would Do Differently

Instructors value honest reflection — it shows you understand the tradeoffs, not just the code. A few honest answers:

  • main.py handles too many responsibilities — game loop, entities, level loading, collision, and saving all live in one file. For a larger project these would each earn their own module, but for a class project the simplicity of a flat structure outweighs the organizational benefit.
  • Collectible rendering shape logic (if collectible.type == "gem" etc.) in ui.py could be replaced with a per-type draw function stored in COLLECTIBLE_TYPES, so adding a new type doesn't require touching the renderer at all.
  • speed_mult is set by the game loop and written directly onto the Player object before each tick. A cleaner approach would pass it as a parameter to Player.update() so the player object doesn't carry state that belongs to the level.
