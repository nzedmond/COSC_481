Geometry Snake

COSC 481 — Presentation Guide & Design Reference

Presentation Structure

  1. Live demo — Run the game. Collect something, die, show the score screen. Let them see what they're about to hear explained.
  2. Folder tour (1 min) — Show the core/, entities/, systems/, rendering/ split and state the rule: logic never imports rendering.
  3. Walk one frame — Trace input → physics tick → collision check → render. This ties everything together naturally.
  4. Go deep on 2–3 design decisions — Don't try to cover everything. Pick the ones you're most confident defending and go deep.
  5. Show the tests — Open tests/ briefly. Mention that geometry.py functions are testable without a window. This signals software engineering maturity.
  6. End with what you'd do differently — Instructors love honest reflection. It shows you understand the tradeoffs, not just the code.

Key Design Decisions to Highlight

1. Logic vs. Rendering Separation

This is the strongest architectural decision. The entities (Player, Trail, Obstacle, Collectible) are pure data — no drawing code anywhere in them. The Renderer class owns all drawing, receives entities, and reads their state. You could swap out pyray for another library without touching a single game logic file.

Data flows one direction: logic → rendering. Rendering state never affects physics.

Why did you separate rendering from logic?

Testability and maintainability. The geometry utilities and collision logic can be unit tested without opening a window. It also means the rendering layer can change independently of game rules.

2. Fixed-Timestep Physics Loop

Physics runs at exactly 60 Hz regardless of frame rate using an accumulator pattern in game.py. Real frame time accumulates into a buffer; physics ticks batch-process when the accumulator reaches FIXED_DT = 1/60 s. The accumulator is clamped at MAX_ACCUMULATOR (0.2 s) to prevent a "death spiral" on slow machines.

What happens if the game runs at 30 FPS or 120 FPS?

Physics stays deterministic. The accumulator catches up with multiple ticks on slow frames, or waits on fast frames. Game behavior is identical regardless of display refresh rate.

3. Sweep-Based Collision — No Tunneling

CollisionManager tests the movement segment (previous position → current position) against obstacles using parametric segment-rectangle intersection from utils/geometry.py. This prevents the snake from clipping through thin walls at high speed, which a simple point-in-rect test would miss.

A broad-phase AABB cull (only test obstacles within 200 px ahead of the player) keeps the per-frame cost low even with many obstacles.

How does collision detection work at high speeds?

We test the full movement segment each tick, not just the current position. This is called a sweep test and it guarantees the snake can't skip through an obstacle no matter how fast it moves.

Do you check for self-collision?

No — and deliberately so. The snake always moves rightward, so x strictly increases each tick. The head can never geometrically reach a previous trail point. Skipping that check is correct, not an oversight.

4. Data-Driven Level Design

Levels are entirely defined in JSON files with a validated schema — obstacles, collectibles, speed curve, camera config, and parallax seed. No code changes are needed to add a new level. 

{
  "name": "Cave Run",
  "length": 5000,
  "speed_curve": [{"x": 0, "mult": 1.0}, {"x": 5000, "mult": 2.2}],
  "camera": {"lookahead": 160, "lerp": 0.08},
  "parallax_seed": 42,
  "obstacles": [...],
  "collectibles": [...]
}

How would you add a new level?

Create a JSON file following the schema, register it in GAME_LEVELS in game.py, and run the test suite. No other code changes needed.

What happens if the JSON is malformed?

The Level loader validates required fields, types, and speed curve ordering at load time and raises a descriptive ValueError before the game starts.

5. Piecewise-Linear Speed Curve

Each level JSON defines a speed curve as a list of waypoints (x world position → mult speed multiplier). Level.speed_multiplier_at(x) linearly interpolates between them. This gives each level a custom difficulty ramp — early sections easy, late sections punishing — without hardcoding anything.

How does the game get harder over time?

The speed curve increases the player's horizontal velocity as they progress through the level. The same obstacles become harder to dodge because you have less reaction time.

6. Particle Object Pool

ParticleSystem pre-allocates 200 particles at startup and recycles them — zero memory allocation during gameplay. When a collectible is picked up or the player dies, the system finds dead particles in the pool and reuses them. If the pool is exhausted, it silently emits fewer particles rather than crashing.

Why not just create particle objects on the fly?

Frequent allocation triggers garbage collection, which causes frame hitches in real-time games. Pooling keeps memory pressure flat and frame times consistent.

7. Trauma-Squared Screen Shake

Screen shake intensity = trauma² × max_offset. Trauma decays over time (trauma -= SHAKE_DECAY × dt). Squaring the trauma value creates a non-linear response: soft rattles at low trauma, violent shakes at high trauma — more perceptually realistic than a linear relationship.

8. Two-Pass Trail Rendering

The trail is drawn in two passes inside TrailRenderer:

  • Glow pass — wider, semi-transparent, covers only the head region. Widens with speed multiplier.
  • Core pass — full trail drawn as a tapered quad mesh. Colors shift from cyan (level start) → magenta (level end) based on progress.

This creates a glowing aura effect without expensive post-processing.

9. Deterministic Procedural Parallax

ParallaxBackground generates its background rectangles using a seeded random number generator. The same seed always produces the same background. Each level can specify its own parallax_seed in JSON, giving each level a visually unique background with no asset files needed.

How One Frame Works

Game.run() — each iteration:

  1. dt = get_frame_time()          (real wall-clock delta, e.g. 0.016 s)

  2. _update_loop(dt)
       match self.state:
         MENU         → handle menu input, transition to PLAYING on selection
         PLAYING      → accumulate dt; run fixed physics ticks:
                          Player.apply_control(input_held)
                          Player.update(FIXED_DT)
                          Trail.update(player.pos)
                          Camera.update(player.pos, FIXED_DT)
                          ParticleSystem.update(FIXED_DT)
                          _check_collectibles()       ← distance-based collection
                          CollisionManager.check_all() ← sweep test each tick
         PAUSED / GAME_OVER / LEVEL_COMPLETE → handle overlay input

  3. _render()
       progress = player.pos.x / level.level_end_x

       Renderer.draw(progress, player.speed_mult)
         ParallaxBackground.draw()    ← screen space (before camera)
         camera.begin()
           _draw_obstacles()
           _draw_collectibles()       ← animated bob, glow, shape
           TrailRenderer.draw()       ← two-pass quad mesh
           _draw_player()             ← two concentric circles
           ParticleSystem.draw()
         camera.end()
       ScreenEffects.draw()           ← screen space (vignette, fade)
       HUD.draw()                     ← screen space (score, progress bar)
       [menu overlay if not PLAYING]

What You Would Do Differently

Instructors value honest reflection — it shows you understand the tradeoffs, not just the code. A few honest answers:

  • Move speed_mult updates out of the game loop and into a dedicated system, so the Game class isn't responsible for both orchestration and per-entity state management.
  • The level_loader.py wrapper around Level adds a thin layer that doesn't do much — those responsibilities could be collapsed.
  • Collectible rendering shape logic (if col.type == "gem" etc.) in renderer.py could be moved into a per-type draw strategy to avoid adding another elif each time a new collectible type is introduced.
